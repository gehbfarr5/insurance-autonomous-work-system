# 项目总体框架 v0.2｜规划基线

> **状态：2026-10-24 总体规划整理版。** 本文是当前业务与协作框架的主要入口，描述已确认的长期方向与待验证的候选模型；不是技术架构、已实现功能或阶段一的需求规格。原 [v0.1](02-project-framework-v0.1.md) 保留为旧链接入口。

## 1. 项目定位

「保险规划师自主工作系统」不是单项工具集合，也不是仅将现有操作自动化。它应在规则和授权内，主动发现值得做的工作、形成建议、组织执行、核实成果，再依据真实反馈持续改进整个工作体系。

人与 AI 同时承担两种关系：

- **共同经营与成长：** AI 不要求用户事先知道完整的获客策略或成功公式。双方共同发现问题、讨论假设、验证业务结果，逐渐提升用户自身的职业判断。
- **授权后的自主执行：** 对明确授权的日常事项，AI 应主动行动、核对结果、处理异常，不因每次细节变化而反复请求人工确认。

这两种关系互补，不等于 AI 独立决定职业方向，也不等于用户必须亲自审批每个步骤。

## 2. 四个业务领域与横向协调

| 领域 | 纳入的工作范围 | 状态 |
| --- | --- | --- |
| **A. 客户经营** | 多来源客户资料、纸质卡片、日常客户库、公司系统按需录入、客户分类、常规电话联系、联系记录、跟进、面对面服务支持 | 业务范围已识别，具体流程未定 |
| **B. 公司信息与业务机会** | 公司活动、产品信息及变动、公告、微信群等来源的通知；识别可能带来的经营机会 | 方向已确认，来源读取方式未定 |
| **C. 内部事务与工作组织** | 主管安排、临时工作、学习培训考试、签到报名、资料提交、会议活动、客户预约及个人日程、其他内部任务 | 业务范围已确认，权限和任务细则未定 |
| **D. 自主运行与持续改进** | 跨领域统筹、异常升级、结果核验、复盘、改进工作方法及受控进化 | 长期定位已确认，实施机制未定 |

**横向原则：** 一件真实工作可以同时涉及多个领域。例如，公司发布活动 → AI 理解活动与价值 → 匹配适合客户 → 按授权组织邀约及报名 → 记录结果和后续服务 → 从效果中改进方案。不要为每个领域造互不相连的独立任务孤岛。

**已知但未选定实现方式的事实：** 个人自建客户库被选作日常客户经营入口；公司「科技个险」仍用于公司侧客户管理与活动等安排，必要时按需录入，两者不要求机械镜像。客户信息来自公司名单、科技个险、表格、微信、通讯录与通话记录、线下交流、主管交付的纸质卡片等；存在来源不代表已自动获得读取权限。

## 3. 经营规划的时间尺度与决策方式

**月度：** AI 依据已有公司活动、客户经营与工作信息，**先提出月度计划草案**；双方讨论、由用户补充一手情境，确认经营方向。

**每周：** AI 自主把方向组织为可执行的近期动作；在月度方向及既有授权内，可增加、取消、调整自己安排的具体工作，并跟踪结果。

**日常：** 以完成已授权任务、记录结果、处理异常为主。用户反馈日常几乎没有显著日程冲突，因此“解决日历冲突”不是主要建设目标。

**动态复评：** 若 AI 发现有依据的新机会、明显效果变化或策略问题，可以在月中主动发起讨论；**改变整体方向仍需双方协商**，不等于可以自动变更客户承诺或公司要求。

## 4. 人机判断权和授权边界

- **用户主导：** 现场职场情境、重要客户关系、面对面交流、重要业务判断及个人职业方向。用户提出的“至少约 60%”是判断权的倾向，不是待实施的数字配额。
- **AI 侧重：** 日常安排、技术判断、已授权的事务执行、跨业务协调、证据收集、主动提出异议与改进。
- **共同判断：** 月度经营方向、重要策略、获客方法与长期工作价值。
- **客户沟通：** 常规电话联系与基础邀约可作为未来 AI 自主能力目标；重要关系互动及需要本人直接交流的场合仍由真人负责。具体电话规则、授权、适用约束和交接机制以后定义。
- **纠正机制：** 用户掌握更多现场细节时，AI 应及时更新判断；可提出有依据的不同意见，但不能以信息不完整的推断压过当事人的一手事实。

公司明确要求、客户已有承诺、授权范围与其他外部义务不因 AI 可修改内部任务计划而自动取消。详见 [人机协作、授权与验证原则](05-autonomy-governance.md)。

## 5. 两个相互促进的运行闭环

**业务经营闭环（长期目标）：** 发现信息或变化 → 识别任务和机会 → 评估价值与权限 → 形成/调整计划 → 自主完成获授权的工作 → 核实结果 → 记录反馈并复盘。

**工作方式进化闭环（长期目标）：** 观察执行中的成本、失败或新机会 → 质疑是否仍该这样工作 → 提出流程改进或替代方案 → 在适当授权与验收条件内验证 → 保留有效做法，撤回无效改变。

`Scout → Architect → Builder → Verifier → Reporter` 只是职责视角：发现、设计、执行、验证、报告。**不代表已经决定五个 Agent、软件框架或技术平台**。

## 6. 如何评价系统真正有效

四个已确认维度：**经营成果、人工减负、客户关系与服务质量、用户本人业务能力成长**。自动化数量和已执行任务数量不直接等于价值；要区分执行证据、实际结果与未经验证的推测。准确性、授权和既有义务是不可随其他成果抵消的约束。

早期首先在明确、有限的工作中建立**可靠执行与减负的证据**，再逐步扩大经营协作的深度；早期也不能忽视客户体验和其他长期价值。

## 7. 发展阶段：方向与待定事项

目前只确认循序发展的**原则**，以下是供后续逐阶段讨论的候选能力路线：

1. **S1：可靠执行与人工减负。** 选择待定的具体试点，证明任务能正确完成和核验，并在失败时妥善处理。
2. **S2：跨领域自主协作与流程改进。** 将相关任务、信息和结果连接起来，减少人力中转，完善自主统筹。
3. **S3：经营策略协作与持续进化。** 更深入开展机会评估、月度经营规划、业务复盘与个人能力成长。

**尚未确定：** 第一阶段业务切入点、阶段数是否固定、先后依赖、时间表、KPI、验收门槛、模型、设备、云服务和系统架构。不同 S 阶段可存在并行基础能力，不应机械解释为只能单线推进。

**命名约定：** 本项目的“业务需求细化工作”（旧 Issue #1 名称曾称 Phase 2）属于**规划工作流**；S1/S2/S3 属于**候选系统能力发展阶段**，两者不是同一套阶段编号。

## 8. 下一步如何从规划进入可执行项目

使用 [阶段与决策关口路线图](../planning/roadmap.md) 确定讨论顺序，用 [业务需求调查入口](../planning/phase-2-business-requirements.md) 收集依据与候选需求，用 [待决事项](04-open-questions.md) 避免将开放问题写成既定方案。

当前“可执行”指**知道下一步要作出哪些决定、需要什么依据、何时允许进入下一步**，不是宣称具体实施细节已经获批。

公开仓库只保存脱敏规划与方法，不放客户个人信息、内部文件、公司凭据和访问令牌。
