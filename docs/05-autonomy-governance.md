# 人机协作、授权与结果验证原则

> **状态：总体规划基线。** 这是业务治理和责任边界，不是某个 Agent 平台的权限配置，也不构成已批准的实际客户外呼或公司系统访问授权。

## 1. 共同判断与自主执行并存

**人主导重要情境，AI 主导获授权的执行细节。**

| 事项性质 | 默认分工 | 原则 |
| --- | --- | --- |
| 客户面对面、重要关系、职场现场判断 | 用户主导，AI 提供建议 | 用户补充的一手信息必须被认真采纳 |
| 获客策略、月度方向、长期价值标准 | AI 先提案，双方讨论确认 | AI 可提出证据充分的不同意见 |
| 日常任务增减、内部工作组织与技术方案 | Agent 在授权范围内自主 | 不因步骤变动而频繁人工审批 |
| 超出授权、改变重大方向或影响对外承诺 | 由用户参与决策 | 未确认前不可按新方向自行执行 |

“至少约 60% 的判断由用户做”是重要业务判断主导权的方向性表达，非配额。

## 2. 授权是具体而有边界的

- **长期规则可以代替重复审批**：在事先明确的目标、动作范围、适用条件及异常升级规则内，AI 可以持续推进工作。
- **允许自主调度，不等于无限自主**：AI 可增减自己的计划事项，却不能仅凭此取消强制工作、修改已对客户作出的承诺或扩大数据访问范围。
- **明确委托可以扩大自主范围**：仅在该事项的权限和约束确实已被用户授权时适用；用户保留暂停、修订或撤回授权的权利。
- **自主电话联系是长期候选能力**：适用于经授权、适合标准化的基础触达；重要、敏感、复杂的客户沟通交由真人。实际触达规则、公司制度、隐私与适用法律需要在设计该业务前核实。
- **用户纠正优先更新情境**：AI 不应反复忽略用户掌握的现场细节；遇可验证的事实冲突，说明理由并共同核对。

## 3. 验证不只看“执行了”

后续任务应能够在业务上区分：**待处理、执行中、已执行待核实、结果已验证、失败或需人工处理**。这是验收原则而不是数据库字段设计。

核实应依据具体业务结果。例如，客户资料“发送到公司 App”与“已在公司 App 中核实存在”不同；电话拨号与成功传达信息不同；报名动作已尝试与报名结果确认也不同。

- **执行证据：** 做了哪些动作，有何可靠记录。
- **结果证据：** 目标是否实际达成，是否存在部分完成或不确定。
- **业务价值证据：** 是否减负、改善服务、促进经营或提升用户能力。
- **异常处理：** 失败、证据不足、越权风险时应暂停该事项、记录并交接，而不是将推测包装成成功。
- **自主改进：** 优化前后需要可以比较，且遵守回滚、审查与授权边界；不将“自己修改了流程”直接视为改进。

## 4. 跨领域协作如何保持可靠

系统未来应针对跨领域任务保留“谁提出、基于什么信息、当前状态、下一个负责人、何时验收”的可追溯关系。具体记录结构、工具和数据保留期限后续确定。

公司业务系统与个人客户库具有不同用途；**业务信息能否进入某一系统**取决于必要性、权限和实际公司规则，不应默认全面复制或从微信、通话等渠道无差别抓取。

## 5. 结果导向，而非指标替代

长期评价维度：经营结果、减负、客户关系质量、个人专业成长。准确性、合规义务及客户权益是基础约束，不能靠提高其他维度的得分抵消。

下阶段需进一步定义的不是繁琐的权限微操作，而是：**哪些业务动作足以独立委托、什么结果算成功、何时必须交回用户**。技术实现不得先于这些事实和授权判断。

## 6. 当前状态

本文件只规定已确认协作原则的概念边界。尚未批准任何实际系统外呼、自动提交、自动读取微信或客户资料行为；未选定模型、设备、外呼供应商或 Agent 编排平台。
