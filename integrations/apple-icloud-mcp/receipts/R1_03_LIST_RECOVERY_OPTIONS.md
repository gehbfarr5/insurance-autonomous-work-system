- **状态**：**仅离线准备**。本文档不执行任何操作；两条路都需要新的明确授权。
- **事实基础**（`R1_03_BOUND_ID_PROBE_RESULT.json` v2，判定 `RESOLVED_ID_NOT_RESOLVABLE`）：
  `9D9A****03F3` 在 MAC-1 上于 2026-11-11T01:54:46Z 不可解析（闸门开启、store 正常时 404 `LIST_NOT_FOUND`）。此前的时间点：11-07 在枚举中（B2）、11-09 返回匹配标识（AG07）、11-10 枚举中缺席（R1）。**这份证据不判定原因**——删除、离开账户、未同步、source 范围变化、最近删除，都未被排除。

## 0. 共同前置（两案都需要，先做这个）

**零读取的人工确认**：由你在任一设备（iPhone/Mac 的提醒事项 App、icloud.com）人工查看这个专用列表现在在哪——在不在「最近删除」、在不在其他设备上、是否同名但换了身份。

- 这是用户侧 GUI 动作，不经过桥、不做枚举、不读事项，**不需要新授权**。
- 它直接决定 A 案是否可行；B 案也在"确认原列表确实没了"之后才值得做（否则会出现两个同名列表）。

**注意**：进入「最近删除」查看/恢复**不在现有授权内**（申请的排除项明确列了这一条）。所以这一步必须由你人工完成，不能由工程侧代做。

## A 案：恢复原专用列表

**思路**：让原列表回来，绑定不动。证据链（AG04/B 系列 → R1 → R1-03 都指向同一个 ID）保持连续。

| 项 | 内容 |
| :--- | :--- |
| 可能路径 | iCloud「最近删除」恢复（删除后 30 天内）；通过系统设置/提醒事项 App 或 icloud.com，由你操作 |
| 关键风险 | **恢复不保证 calendar identifier 保持原值**。若恢复后 ID 变了，绑定仍指向旧 ID，结果还是 404——A 案白做，仍要落到 B 案 |
| 必要前置 | ① 你确认列表在最近删除且未过 30 天；② 恢复由你完成（桥是只读的，恢复也不是桥的操作）；③ 恢复后**一次最小核验窗口**：与 R1-03 同构（同参数、同预算 120 s、同时限 30 s、同零枚举约束），条目请求 ≤3，判定"原 ID 是否重新可解析" |
| 验收 | 核验窗口里 open 相位对 `9D9A****03F3` 得 200（0 条或 n 条皆算"可解析"，n>0 只记计数立即停） |
| 回退 | 恢复失败、或恢复成功但 ID 变了 → **不改任何配置**，原绑定原样保留（指向旧 ID、继续 404，无害），转 B 案。不需要任何回滚动作 |

**A 案的代价**：一次核验窗口（需要一次开窗授权）；收益：若 ID 保持，零配置变更、证据链完整。

## B 案：新建专用列表并改绑

**思路**：承认原列表回不来（或 ID 回不来），新建一个列表，把绑定指向它。

| 项 | 内容 |
| :--- | :--- |
| 必要前置 ① | 新列表由**你**在提醒事项 App 创建（Apple 写入由用户完成；桥只读、工程侧不做任何写入，这条在现有授权里明确排除） |
| 必要前置 ② | **获知新列表 ID 的授权路径**——这是 B 案的关键缺口：R1-03 禁止账户级枚举，而新 ID 目前没有任何渠道可读。可行方式：(i) 你明确批准**一次性**的单次枚举（与 R1 同款：只返回列表 ID/名称，不读任何事项，之后立刻回到禁止状态）；或 (ii) 你从其他既有授权产物提供 ID。**没有这一步，B 案无法启动** |
| 必要前置 ③ | 改绑是**配置变更**：修改 plist 的 `EVENTKIT_BRIDGE_ALLOWED_LIST_IDS` 与 `EVENTKIT_BRIDGE_BINDINGS` 两行 + 重载。这超出"业务闸门单键"的范围，需要单独批准，且按申请 §3.1 的来源规则写入（plist 优先） |
| 必要前置 ④ | 改绑后**一次核验窗口**：target = 新 ID，期待 200/0；canary 可选 |
| 验收 | 核验窗口 open 相位对新 ID 得 200，绑定配置哈希前后成对记录 |
| 回退 | 改绑前对 plist 与 config 各做 0600 备份；任何一步失败 → 恢复备份 + 同一入口重载 + 行为验证。新列表**保留不删**（删除是 Apple 写入，不在范围）。旧绑定值逐字记入回执，保证可精确还原 |
| 附带代价 | 证据链在"列表身份"上断裂：旧 ID 的历史证据（AG04/B2/AG07/R1/R1-03）从此指向一个不再绑定的 ID。改绑回执必须写明"绑定目标变更于 <日期>、由 <授权> 批准"，否则后来者会把旧证据误读为对新列表的结论 |

## 3. 取舍对照

| 维度 | A 案：恢复原列表 | B 案：新建并改绑 |
| :--- | :--- | :--- |
| 证据连续性 | 保持（同一 ID） | 断裂（需在回执里显式声明改绑） |
| 需要的新授权 | 一次核验窗口 | 一次性 ID 发现 + 配置变更授权 + 核验窗口（三项） |
| 成功的前提 | 列表在最近删除且 **ID 恢复后不变**（不确定，只能测） | 不依赖原列表状态 |
| 主要风险 | ID 变化 → 前功尽弃，仍走 B | 枚举一次（哪怕只读 ID）；配置变更多两行 |
| 失败回退 | 无损（不动配置） | 有备份可还原；新列表留着 |
| 对"未同步/换身份"情形 | 可能直接失效（列表根本没删） | 会造成重复列表（旧的哪天又同步回来） |

**顺序建议**（不是判定，是依赖关系）：先做 §0 的人工确认——它不花授权、决定 A 是否可能；若 A 可行，先试 A，ID 保不住再走 B；若确认列表确实已删除且无法恢复，B 是唯一路径，先谈前置 ② 的授权方式。
