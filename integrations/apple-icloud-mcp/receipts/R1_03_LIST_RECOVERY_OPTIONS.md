## A 案：恢复原专用列表

**思路**：让原列表回来，绑定不动。证据链（AG04/B 系列 → R1 → R1-03 都指向同一个 ID）保持连续。

| 项 | 内容 |
| :--- | :--- |
| 执行能力 | **恢复操作**需要 Apple 数据写能力：工程侧桥是只读的、工程侧当前无任何写授权；具备该能力的主体是用户侧 GUI（提醒事项 App / icloud.com）。**核验**（开窗 + 条目探测）工程侧已有全部工具与流程（R1-03 v6 体系），可直接执行 |
| 必要授权 | ① **恢复操作**：当前不在任何已批准范围内（申请的排除项明确包含进入/恢复「最近删除」），需单列批准或由具备写能力的主体自行完成；② **核验窗口**：一次开窗授权（同 R1-03 v6 参数：预算 120 s、操作时限 30 s、零枚举） |
| 可能路径 | iCloud「最近删除」恢复；通过系统设置/提醒事项 App 或 icloud.com |
| 已知风险 | **恢复后 calendar identifier 不保证保持原值**。若恢复后 ID 变了，绑定仍指向旧 ID，结果还是 404——A 案的核验会如实报出，仍要落到 B 案 |
| 未知项（据实保留） | 列表是否仍在「最近删除」且未过保留期——**未核实**；保留期的实际值——**未核实**（通常说法是 30 天，未经本次任何测量支持）；恢复后 ID 是否保持——**只能靠核验窗口测**，事先无法保证 |
| 验收 | 核验窗口里 open 相位对 `9D9A****03F3` 得 200（0 条或 n 条皆算"可解析"，n>0 只记计数立即停） |
| 回退 | 恢复失败、或恢复成功但 ID 变了 → **不改任何配置**，原绑定原样保留（指向旧 ID、继续 404，无害），转 B 案。不需要任何回滚动作 |

**A 案的代价**：一次核验窗口；收益：若 ID 保持，零配置变更、证据链完整。

## B 案：新建专用列表并改绑

**思路**：承认原列表回不来（或 ID 回不来），新建一个列表，把绑定指向它。

| 项 | 内容 |
| :--- | :--- |
| 执行能力 | **新建列表**需要 Apple 数据写能力（同 A 案，工程侧桥只读、无写授权）；**ID 发现**：工程侧可用既有受限客户端执行单次枚举（若获批准），或由其他渠道提供 ID——后者是否存在**未知/待定**；**改绑**（改 plist 两行 + 重载）与**核验窗口**：工程侧已有全部工具，可直接执行 |
| 必要授权 | ① **ID 发现**：一次性单次枚举批准（与 R1 同款：只返回列表 ID/名称，不读任何事项，用后回到禁止状态），或等效的 ID 来源；② **配置变更**：修改 plist 的 `EVENTKIT_BRIDGE_ALLOWED_LIST_IDS` 与 `EVENTKIT_BRIDGE_BINDINGS` 两行 + 重载——超出"业务闸门单键"的范围，需单独批准，按申请 §3.1 的来源规则写入（plist 优先）；③ **核验窗口**：一次开窗授权，target = 新 ID，期待 200/0，canary 可选 |
| 已知风险 | 枚举一次（哪怕只读 ID）；配置变更多两行；**证据链在"列表身份"上断裂**——旧 ID 的历史证据（AG04/B2/AG07/R1/R1-03）从此指向一个不再绑定的 ID，改绑回执必须显式写明"绑定目标变更于 <日期>、由 <授权> 批准" |
| 未知项（据实保留） | 新列表 ID（尚不存在）；ID 发现的可行方式（枚举之外是否有其他渠道——**未核实**）；原列表若日后重新同步回来，会出现两个列表——发生与否**不可预知** |
| 验收 | 核验窗口 open 相位对新 ID 得 200；绑定配置哈希前后成对记录 |
| 回退 | 改绑前对 plist 与 config 各做 0600 备份；任何一步失败 → 恢复备份 + 同一入口重载 + 行为验证。新列表**保留不删**（删除是 Apple 写入，不在范围）。旧绑定值逐字记入回执，保证可精确还原 |

## 3. 取舍对照

| 维度 | A 案：恢复原列表 | B 案：新建并改绑 |
| :--- | :--- | :--- |
| 证据连续性 | 保持（同一 ID） | 断裂（回执须显式声明改绑） |
| 需要的新授权 | 恢复操作（或由有写能力的主体完成）+ 一次核验窗口 | ID 发现授权 + 配置变更授权 + 核验窗口（三项） |
| 成功的前提 | 列表仍在且**恢复后 ID 不变**（未核实，只能测） | 不依赖原列表状态 |
| 主要风险 | ID 变化 → 前功尽弃，仍走 B | 枚举一次；配置变更多两行 |
| 失败回退 | 无损（不动配置） | 有备份可还原；新列表留着 |
| 对"未同步/换身份"情形 | 可能直接失效（列表根本没删） | 会造成重复列表（旧的哪天又同步回来） |

**依赖关系**（不是判定）：列表现状的确认决定 A 案是否可能——它属于两案之外的第一个待办，由谁、经什么授权完成**待定**；现状确认之后，A 可行先试 A，ID 保不住再走 B；确认已删则只谈 B 的授权。
