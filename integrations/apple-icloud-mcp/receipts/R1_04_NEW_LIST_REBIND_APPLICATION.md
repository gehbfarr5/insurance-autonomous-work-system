### 3.3 匹配规则

## 4. 改绑与回退

### 4.1 成对变更

| 键 | 旧值 | 新值 |
| :--- | :--- | :--- |
| `EVENTKIT_BRIDGE_ALLOWED_LIST_IDS` | 旧列表 ID（掩码 `9D9A****03F3`） | 新列表 ID |
| `EVENTKIT_BRIDGE_BINDINGS` | `旧ID:旧sourceID:calDAV:iCloud` | `新ID:新sourceID:calDAV:iCloud` |

两键同时、一次改绑完成，不出现"白名单已换、绑定未换"的中间态。权威来源按既有 plist 优先规则判定（R1-03 实测 `gate_source=launchd_env`）；`r1_rebind.sh` 在两键于 plist 与 config 同时存在时拒绝执行。

### 4.2 验证（v3：范围冲突经执行路径排除）

改绑的每次条目读取都只针对**新列表**；**旧列表的条目端点在整条执行路径上一次都不被请求**：

- **前置检查（改绑前）**：`GET /reminders/lists` 带令牌，期望 403（client `gate` 命令）。枚举端点**只含列表元数据**，任何闸门状态下都不可能携带任何列表的事项内容——这个证明**读不到一条提醒事项**。403 的含义是"闸门关闭，或 TCC 被拒"；后者同样内容安全（TCC 拒绝时任何请求都拿不到事项内容），且会在 W1 暴露。
  - **为什么弃用旧 ID 前置探针（v2 方案）**：旧 ID 在当前白名单上，它的 403 确实严格证明关闸；但若闸门**意外开着**，这次条目读取会触达旧列表的条目端点——与"事项读取仅限新列表"的范围冲突，且无法通过执行路径排除。枚举 403 检查给出同等强度的关闸证明（唯一歧义是 TCC 拒绝，而 TCC 拒绝本身内容安全），把范围冲突**从执行路径上消除**。
- **后置探针（改绑后，新 ID）**：`probe --phase post --expect GATE_RESTORED_CLOSED`。改绑后新 ID 是唯一在 allowlist 上的 ID：allowlist 通过后的 `PERMISSION_DENIED` 证明闸门对新绑定关闭。观察到 `LIST_NOT_ALLOWED` 说明重载未生效 → 失败回退。该读取对象是新列表——即使闸门意外开着，读取范围仍在授权之内。
- **回退验证（恢复备份并重载后，两步按序）**：① 枚举 403（闸门已关，零事项内容）；② 新 ID 探针 `--phase post --expect BLOCKED_NOT_ON_ALLOWLIST`——回退后新 ID 必须在**闸门检查之前**被（旧）白名单拒绝，`LIST_NOT_ALLOWED` 即"旧白名单已回到进程内"的行为证明。若返回 `PERMISSION_DENIED` 则说明新白名单仍在进程内，回退未生效 → CRITICAL。
- 另有 `/health` 200 + `store=production`、进程身份（pid 变更记录）。**"绑定真的可用"由 W1 的 200/`[]` 证明**，改绑步骤本身不声称这一点。

### 4.3 回退与保留（v2 明确条件；v3 更新回退验证方式）

- 改绑任一步失败 → `r1_rebind.sh` 自动恢复备份（两键回旧值）→ 同一入口重载 → 按 §4.2 回退验证（枚举 403 + 新 ID `BLOCKED_NOT_ON_ALLOWLIST`）；验证失败也如实报 CRITICAL（磁盘/进程可能分叉，等人工），**从不把失败报成成功**。
- **成功后新绑定保留**：`r1_rebind.sh` 验证通过即结束，不回滚；新绑定是 R1-04 之后的常态配置（A8）。
- **W1 失败时恢复旧配置的条件**（仅当 W1 之后需要回退时适用）：
  - `RESOLVED_SOURCE_IDENTITY_CHANGED`（来源身份与绑定不符）→ **恢复旧绑定**：用改绑备份把两键写回 → 重载 → 按 §4.2 回退验证。旧 ID 已 404，恢复后读能力依旧是失效状态——这是**已知且可接受的**，目的只是回到 R1-03 之后的既知基线。
  - W1 得 UNKNOWN 分类（`BLOCKED_*`/`ERROR_*`）→ 只读核对一次、禁止重试，绑定**保持新值不动**，等人工决定（新列表本身已验证存在且同账户，盲目回退旧失效绑定没有收益）。
  - 无论哪种：新测试列表都**保留**，不删除。
- 最终核验：plist 与改绑前备份逐字节比对，**除两键外必须一致**；不一致即报失败。
- 旧绑定完整值记入私有日志与改绑回执（掩码进公开层），任何时候可精确还原。

### 4.4 超时恢复（v3 新增；与 `r1_gate.sh` 有意不同）

`r1_gate.sh` 的超时只留下一个键，其安全值自明（写回 `false`）；**改绑超时可能留下"磁盘已写入新键对、进程仍在跑旧值（或相反）"的分叉**，两种状态都不自明安全。因此改绑的超时出口（exit 8）是一条**可执行的恢复序列**：

1. 操作时钟耗尽（`--op-timeout`，默认 30 s）→ 在途命令连同子进程被杀 → 进入恢复；
2. **恢复备份写回磁盘**（两键回旧值）；
3. **独立恢复时钟内重载一次**（`R1_RECOVERY_TIMEOUT`，默认 45 s——操作时钟已耗尽，恢复用自己的预算，从不无界）：bootout（容忍失败）+ bootstrap，或 kickstart；
4. **验证恢复结果**（与回退验证同一组、范围安全）：`/health` 200（服务健康）→ 枚举 403（闸门关闭）→ 新 ID 探针 `BLOCKED_NOT_ON_ALLOWLIST`（旧白名单确实回到进程内）；
5. 全部通过 → 回执记 `recovery.verdict = VERIFIED`（退出码仍为 **8**：超时永远不是成功）；任一步失败 → 回执如实记 `FAILED_OR_NOT_ATTEMPTED` + CRITICAL（磁盘/进程可能仍分叉，等人工决定）。

恢复期间的每次读取（1 health + 1 枚举 + 1 新 ID 条目）同样逐次记账（§7）。隔离测试 R7 场景覆盖"重载中途超时"：stub launchctl 第一次 kickstart 睡眠 30 s 被 run_bounded 击杀 → 恢复序列完整执行并 VERIFIED——磁盘回旧键对、服务健康、闸门关闭、旧白名单回到进程内。
