## 2. 已确认的整体方案

| 主题 | 用户确认的方向 |
| --- | --- |
| 助手能力 | 观察页面、理解任务、根据反馈行动；不限定为固定脚本 |
| 新任务 | 符合既有授权规则即可自主判断和处理；超出范围或无法判断才交接，不要求新任务一律首次审批 |
| 启动方式 | 按约定周期主动检查和安排获准任务，无需用户逐日提醒；具体时间后定 |
| 不确定状态 | 先自主核查，确认未成功且重试安全才重试；仍不明则暂停该项，其他独立任务继续 |
| 通知方式 | 紧急异常及时通知，非紧急事项集中交接；正常完成不逐项打扰 |
| 推进方式 | 有限任务先跑通，验证执行、结果核验与异常恢复，再逐步扩展 |
| 云端资料处理 | 允许云端工具处理所需资料；不限定本地运行。公开仓库仍不保存原始业务资料与凭据 |

概念流程：获准来源发现任务 → 判断范围及规则 → 核对当前状态 → 执行获准步骤 → 核实结果 → 收尾或交接 → 复盘。此为目标工作流程，不是假称已经观察到的 APP 实际流程。

## 4. 责任与授权框架

用户保留重要业务判断、关系互动、范围调整、授权与撤回决定；Agent 负责获准范围内的发现、组织、执行、核验、异常处理和提出改进。

用户委托意愿、公司允许、系统访问条件、具体实施授权是不同事项。现有确认解决其对应方向，不自动授权购买服务、安装部署、连接设备、操作账号、对外联系或提交生产数据。

P4 可按批次建立授权范围，无需重复审批已获准的例行动作。授权至少明确目标、允许动作、必要数据、适用条件、结果要求、停止与交接方式。范围外或无法判断的动作先交接。任务名称不能代替动作含义、公司义务或事实真实性判断。

## 5. 结果、异常与恢复框架

| 层次 | 可作出的判断 |
| --- | --- |
| 已尝试操作 | 有动作记录，不表示成功 |
| 页面显示完成 | 有明确页面反馈，效力须按任务核实 |
| 结果已确认 | 对应任务、账号、日期/周期的结果符合适用要求，有可核对依据 |
| 真实业务价值 | 需要实际减负或业务反馈，不能由 APP 完成状态推导 |

部分完成须分项记录；证据不足标为状态不明。APP 完成不证明真实拜访、实际学习或个人技能提升。不得掩盖失败、用默认值或乐观推断包装成功。

超时、反馈冲突、重复风险、登录失效、页面变化及权限不明时，按已确认原则核查、暂停对应动作或交接。交接包括已做动作、已确认结果、未完成部分、风险、已知期限、接手人及恢复条件。

停止可针对单任务、类别或全部运行。恢复先核对权限与真实状态，不盲目重放。软件回退不能等同于撤销公司侧已提交结果；具体撤销与更正能力在对应流程确认。

## 6. 方案取舍与资源原则

分析推荐：以能按反馈行动的助手为总体方向，用明确任务规则约束；稳定步骤可使用确定性流程。公司正式可用接口如被发现，可作为对应任务的路径备选，不假设存在。

执行资源按用户选择优先比较完全云端化；云端 Android 的托管与自管方式仅为初查候选，未选产品。Pixel 独立执行为后备路线，旧 Mac Server 中转方式不默认继承。

比较依据：业务适配、注入与 APP 兼容、结果可核验、状态恢复、人工维护、设备依赖、许可、凭据与访问控制、实际资源成本。设备更少不必然代表总负担更低。费用、工时、周期及成功率均不编造。

复用已有业务基线与成熟能力；按实际版本和流程适配；避免默认继承旧代码或因通用 root 能力就断言注入及 APP 可用。具体技术研究和许可核对在 P4 对应任务启动时进行，不要求本阶段完成。

## 7. 验证与扩展原则

已确认先本地模拟判断、交接和停止逻辑，再经对应授权进行有限真实验证。模拟、人工观察、自动运行与正式业务结果分别记录；不存在测试环境时，不能以模拟替代真实结果。

不在生产中故意制造重复提交或错误数据。验证覆盖正常完成、已有结果、超时、不确定、部分完成、中断与恢复；具体样本和判据在任务设计时确定。

扩大范围需有实际证据：结果准确、无未经授权动作、可控制重复影响、异常可接手、停止恢复有效、实际减少人工负担。未知状态不得报完成，完成次数不得代替价值。量化门槛依据真实条件后定。

## 8. 递延到 P4 的事项

| 事项 | 在何时解决 | 不能带着缺口做什么 |
| --- | --- | --- |
| 首批任务的具体边界、触发、输入、输出与动作含义 | 对应任务设计时 | 不能按名称猜测并执行 |
| 实际页面、完成证据与异常反馈 | 获准观察与有限验证中 | 不能在证据未明时宣称成功 |
| 原注入模块位置、代码、框架及版本 | 云端执行环境技术研究时 | 不能假设历史模块可直接迁移 |
| 云端兼容性、供应商、许可与实际成本 | 选型及采购决定前 | 不购买、部署或宣称可替代 Pixel |
| 设备连接、OCR、客户录入与资源冲突 | 开展对应流程时 | 不自动扩展本轮任务或数据用途 |
| 具体授权、身份验证、记录存储与通知渠道 | 对应访问或运行前 | 不默认访问系统、发送消息或上传凭据 |
| 时间安排与量化验收 | 任务与资源条件明确后 | 不作无依据承诺 |

递延是分批确定细节，不是免除条件，也不要求用户预先写完整操作手册。P4 中助手先调查可发现的信息，只就会影响范围、权限或结果的关键缺口集中提问。

## 9. P3 关口结论与 P4 接续

正式决策：用户确认按当前框架完成 P3 并进入 P4。依据是框架层面的范围、方案方向、职责、授权、证据、异常、验证与扩展原则已形成并获确认；不要求将任务级细节提前全部定稿。

P3 收尾不表示实际流程已全部查明、云端方案已证明可行、新系统已实现或通过验收。原始任务要求中需要实际观察的部分明确递延，不能标记为已经完成。

建议 P4 接续顺序：

1. 以本框架建立首个有限工作包，细节调查随包推进；不同时扩展所有业务域。
2. 优先研究云端执行所需条件，核对现有资料并比较成熟路径；若不满足再评估 Pixel 独立执行。
3. 明确该包的具体方案、资源、结果证据和相应授权，再开展实施与验证。
4. 据真实结果决定继续、暂停、调整或扩大，不以阶段名称代替验收。

P4 是实际落地阶段，可以按工作包开展具体设计、开发与验证，无需另设一整轮总体框架阶段。实施范围和必要授权随工作包明确；进入阶段本身不等于立即批准所有开发、部署、生产动作或服务购买。P4 不被定义为项目最终阶段，后续是否增设阶段由实际结果决定，不预设新的编号。
