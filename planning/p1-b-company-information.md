# P1-B｜公司信息与业务机会（具备阶段性收尾条件）

> 更新时间：2026-10-24。来源为用户对实际微信群工作流的描述及本轮提供的截图；**仅记录去标识化的业务模式**。本公开仓库不得上传原始群截图、群成员或客户姓名、名单、二维码、内部活动详情、报名链接、保单/成交信息。

## 一、已确认的实际业务事实

1. 公司业务通知**分散在微信群**，且群内杂讯较多。用户目前主要依靠自己查看、筛选和跟进，因此维护信息流本身费时费力、容易让有价值的临时通知被淹没。
2. 用户认为**其他人员的开单喜报/表彰信息**通常不要求自己立即执行，是当前目标下的低价值噪声；这是对当下个人工作价值的判断，不等于信息在所有情境下毫无用途。
3. 群里还会有**高净值客群活动、报名名额动态、行程总结**等消息。用户现阶段缺少匹配的目标客户，某些高净值客群活动对他当下实际业务价值较低；这一相关性会随着客户结构、经营目标变化而变化，不应永久屏蔽所有同类活动。
4. 真正需要采取行动的活动有时**通知较临时、需要抢在报名截止前完成报名、名额有限**；关键信息经常以**海报**呈现，报名入口可能是图片中的二维码。仅靠文字消息摘要可能遗漏业务行动条件。
5. 用户希望未来 Agent 不只发现通知，还能在合适的情境下**筛选值得关注的消息、处理活动报名、安排日程**，使信息流转化为实际完成的工作。
6. 用户当前已**有时将海报二维码对应的报名页面交给 Agent 处理**，属于现存的部分辅助实践；尚无证据证明 AI 已能自主读取所有群消息、独立完成报名到日程的闭环，或持续保持可靠性。
7. 活动通常需要结合**当前客户结构、公司实际安排及用户经营目标**判断价值；需要区分“需要用户马上行动的通知”“暂时低相关消息”“活动结束后的结果播报”，不把所有信息都视为待办事项。
8. **报名对象可能是用户本人，也可能是用户代具体客户报名，两种情况都真实存在，取决于活动性质。** 不应把所有报名统一理解为用户本人参会，也不应假定存在客户就必然需要代报。具体需要哪些报名信息、由谁确认决定及如何获得有效报名反馈，留待后续针对实际活动研究。

## 二、脱敏实例与业务效果（不是实际报名执行记录）

- **场景 1：高端客群出行活动的报名与剩余名额通知。** 这类内容会占用微信群屏幕空间，但因用户当前没有足够匹配客群，现时关注度较低。
- **场景 2：公司活动结果和其他同事业绩播报。** 属于用户目前认为干扰阅读、通常不触发本人任务的信息。
- **场景 3：活动权益/产品介绍会的海报与临时报名提醒。** 需要查看参加对象、时间、报名要求、截止点和入口，及时决定是否参与；表单可能通过二维码打开。**截图仅证明存在这类业务信息，不证明相关活动一定适合该用户、报名已经成功或信息内容可作为已核实的产品承诺。**

## 三、尚待核对的最小业务问题

1. **已确认报名对象（无需重问）：** 用户本人报名和代客户报名两种情况都存在，依据活动决定。具体不同活动的字段、人员确认及业务流程属于 P2/P3 定向补充项。
2. **信息进入的广度：** 是否主要依赖这类经营群，或者产品群、主管群和其他通知渠道也存在类似人工负担？不在此推定群访问权限和具体技术。
3. **完成核验：** 用户有晚宴等活动报名成功检查的实际经验，Agent 辅助办理的主观失误率很低。不同活动的具体成功反馈与例外处理留待 P2/P3 按场景核查。
4. **时间条件：** 临时活动和名额变动何时真正要求立即处理，何时应先征求用户决策；具体授权细节待 P3。

## 四、候选跨领域业务链条（非已批准的执行规则）

微信群的信息 (B) → 依据当前客户/经营方向判断是否值得行动 (A/B) → 区分本人参会报名或代客户报名、确认具体对象 (A/B/C) → 处理适合的报名及结果确认 (B/C) → 按活动性质安排本人或客户相关日程、必要时邀约 (A/C) → 检视是否实际完成 (D)。

这不是已运行的自主化流程；**没有预先选定 S1 试点、微信读取技术、直接扫码报名权限、自动访问公司系统的授权。** 不将各类消息混同为需要即时处理的任务。
