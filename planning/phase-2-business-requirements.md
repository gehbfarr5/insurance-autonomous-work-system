# 阶段二：业务需求地图与优先级梳理

**状态：讨论入口，尚未开始正式需求分析。**  
**目的：** 建立下一阶段调查范围和预期产出，不预设需求答案、优先顺序或方案。

## 调查范围

以目前初步识别的四类业务领域为入口：

1. **客户经营：** 多来源客户资料整理、客户资料批量录入、客户分类筛选、活动邀约与跟进、客户联系记录和后续关系维护。
2. **公司信息管理：** 公司活动通知、产品信息与更新、业务公告和重要信息整理。
3. **内部事务：** 培训任务管理、活动报名和资料准备、公司系统内的重复性操作。
4. **系统运行与改进：** 任务调度、异常处理、运行记录、结果核验、自主优化与版本管理。

以上仅是初步领域和示例工作，不代表完整需求清单或优先级。

## 待调查主题

- 各领域真实任务、当前流程、参与者和信息来源
- 任务频率、人工耗时、重复环节、等待与主要困难
- 期望业务结果及可观察的验收证据
- 规则、异常、人工判断与升级处理情形
- 数据范围、访问条件和实际适用的外部约束
- 现有设备、系统、资料和历史项目的现实状态
- 比较价值、成本、风险和可行性的优先级依据

这些是调查提纲，具体问题和回答由下一阶段工作形成。

## 预期产出

- 按业务领域组织的任务与流程地图
- 当前流程、主要问题、信息来源和参与环节的证据记录
- 关键例外、约束和需要人工判断的情形
- 需求之间的依赖或共同问题
- 经讨论的优先级及其依据
- 尚待验证的问题和后续调查事项

本文件不提前填写这些结论。

## 完成标准

- 调查覆盖四个已识别领域，并标明未覆盖之处。
- 描述区分事实、用户判断和待验证假设。
- 候选需求说明目标、当前依据和预期结果；未确认内容标记为待调查。
- 优先级由用户讨论确认并记录依据，不由本入口文档代为决定。
- 产出经过用户检查，不把规划设想描述成已实现功能。

## 需求访谈记录（2026-10-23）

### BR-001：客户经营优先关注的工作（已确认）

- 用户首先提出最希望 AI 承担的两类工作：**客户信息记录**与**打电话／通话**。
- 初步将二者作为一个可能相互关联的客户经营闭环研究：客户信息 → 联系客户 → 通话结果记录 → 跟进与信息更新。该流程仅为**待验证的初步假设**，不预设最终工作流。
- 两类工作的现有渠道、信息来源、去向、实际流程、耗时和优先级尚待详细访谈，不能将已列出顺序解释为正式优先级排序。

### BR-002：客户电话联系的长期自主性目标（已确认）

- 用户明确选择：**高度自主客户联系**。
- 期望 AI 尽可能自主完成客户联系、实际通话沟通、通话信息记录以及后续跟进；用户主要介入例外情况及重要判断。
- 这是**长期业务能力目标**，并非系统已建成、当前拥有外呼能力或已经选择具体通信技术。
- 电话沟通渠道、工作边界、客户触达规则、异常交接、记录形式、回访闭环和验收证据均待后续讨论，并以实际公司指导和可用渠道为约束。

### BR-003：双系统客户信息维护（已确认，2026-10-23）

- 用户确认：客户信息需要在**公司「科技个险」App**和**个人客户管理工具**两边记录与维护，不是二选一。
- 这是一项双系统维护的业务需求；暂不假设两边应存放完全相同的信息，也不预先确定数据库、同步方向、主数据源或具体自动化技术。
- 待澄清：两套系统分别承担什么用途、各自必须保存什么信息；记录更新从何处触发，是否需要双向更新，出现不一致时如何处理；通话记录及跟进事项分别应写到哪里。

### BR-004：双系统的业务定位（已确认用途，2026-10-23）

- **公司「科技个险」**：录入和维护客户信息可用于公司侧客户管理，并支持客户参与公司相关活动或安排。
- **个人自建客户库**：用于更方便、灵活的客户管理，并为不同 AI Agent 的协作及未来功能扩展提供基础。
- 两个系统的作用并不完全相同；不能仅以“完全镜像同步两套客户信息”替代业务需求分析。
- **仍待讨论**：个人库是否作为日常客户经营的主要工作入口；哪些数据必须进科技个险；两个系统的数据流向、更新频率、冲突处理及 Agent 的读写范围。

### 下一轮访谈重点

确认理想工作模式中客户资料的主要工作入口：以个人自建库组织客户经营并按需要更新公司系统，或两套系统并行操作，或根据业务场景灵活切换。此处尚无定论。

### BR-005：个人客户库作为日常主要工作入口（已确认，2026-10-23）

- 用户明确选择：**个人自建客户库作为日常客户管理的主要入口**。
- AI 以自建库支持客户资料维护、联系与跟进等日常工作，并根据具体公司业务需要，**按需将相关信息录入或更新到「科技个险」**。
- 「科技个险」继续承担公司客户管理、活动参与及业务安排等用途。
- 这是**业务工作入口的选择**，不等于已确定数据库产品、技术上的唯一主数据源或单向同步策略。
- 后续需要逐项明确：客户资料来源、字段范围、公司系统录入触发条件、更新冲突处理、通话记录去向，以及自主任务的验收证据。

### 下一轮访谈重点

梳理客户信息的实际来源与进入自建库的路径；优先了解当前使用中的渠道，不预设具体技术方案。

### BR-006：客户资料来源范围（用户确认，2026-10-23）

用户确认当前实际客户信息来源涵盖：

1. 公司提供的客户名单或存量客户资料；
2. 公司「科技个险」App 中已有的客户信息；
3. Excel、WPS 或其他表格；
4. 微信聊天、微信群或联系人；
5. 手机通讯录及通话记录；
6. 线下活动、客户面谈及手动记录。

以上确认的是**实际存在的信息来源**，不代表 AI 现已具备自动访问、读取、录音、转写或同步这些来源的能力，也不代表每一来源都应无差别自动采集。

**待讨论：** 各来源的实际数据结构、重复情况、资料更新频率、客户识别与合并规则、授权访问条件，以及哪些来源最值得先打通。

### 下一轮访谈重点

了解当前客户信息最突出的问题（如重复录入、分散难查、信息过期、通话后难以记录、无法确定跟进对象），再讨论信息汇聚的业务目标与优先级。

### BR-007：主管提供的纸质手写客户信息卡（重要来源，2026-10-23）

**用户确认的现状：**

- 主管提供的**纸质客户信息卡／客户信息本**是客户资料的一个**主要且数量较大的来源**，应从 BR-006 的笼统「线下手动记录」中单独列出。
- 信息卡为**预先印刷的表格或卡片**，随后由人手写填写；实际材料中可能出现**手写内容与印刷文字重叠**。
- 用户过去曾为这一来源建立基于 **OCR → 客户信息录入** 的自动化流程。
- 既有 OCR 方案的明显困难是**混合手写与印刷内容，尤其两者重叠**时的识别问题。
- 用户明确表示本次是重新规划，**不应直接沿用旧 OCR 流程**；未来应从更快捷、可靠地完成客户信息录入的业务目标出发，重新评估方法。具体识别技术和流程属于后续讨论，不在此阶段定案。

**待进一步调查：** 卡片实物样式及变体、字段与填充规律、典型数量与新增频率、拍摄或扫描现状、录入去向、错误核验方式，以及现有 OCR 方案的可复用经验。不得在未验证样本前承诺自动识别准确率。

**优先级提示：** 用户明确该来源占比较大、是主要来源之一；应列为后续重点调查对象，但尚未与其他需求完成正式优先级排序。

### BR-008：纸质客户信息卡的实际交付形式（已确认，2026-10-23）

- 用户通常收到的是**纸质客户信息卡原件**，而不是主管预先拍摄的电子图片。
- 当前由用户自行完成**拍照或扫描**，然后才可能进入信息识别与录入环节。
- 业务分析应区分「纸质材料数字化采集」与「混合印刷／手写内容理解及结构化录入」两段，不能只优化 OCR 而忽略批量采集的人力成本。
- 尚待确认：单次收到的卡片数量与频率、拍摄环境、卡片是否双面、是否需要保留原件、采集耗时、批量操作中的主要阻碍。

### BR-009：纸质信息卡批次规模不固定（已确认，2026-10-23）

- 用户确认主管每次提供的纸质客户信息卡**数量不固定，批次之间差异较大**。
- 因此不宜仅按固定数量或固定批处理规模规划工作流；后续应兼顾少量快速采集与较大批次集中处理。
- 尚未掌握典型批次数量、上限、出现频率或平均耗时，不能据此估算吞吐量与节省工时。
- 下一轮可重点调查纸质卡片目前的采集、整理、识别、核对、录入过程中最费时或最容易出错的步骤。

### BR-010：历史纸质客户卡自动化的真实流程与瓶颈（用户补充，2026-10-23）

**重要更正：此前的旧流程并非尚未跑通。用户明确表示：历史 OCR 自动化从识别、信息解释到科技个险录入，整体流程已经跑通。**

#### 已有流程（历史实况）

1. **一加 15（OnePlus 15）**：拍摄主管提供的纸质客户信息卡，将照片通过远程连接传给 MacBook。
2. **MacBook**：整理、打包照片与中间数据，连接其他执行环节；正则与其他处理细节交由 server 执行。
3. **百度 OCR**：提取信息卡中的印刷字与手写字。总体识别效果尚可，混合或重叠文本更难，但并非最主要瓶颈。
4. **正则匹配**：尝试确定信息所在的表单字段／填写位置，是旧流程中较难维护的一环。
5. **DeepSeek 语义分析**：帮助判断字段含义并确认复杂保单内容，尤其保险名称、手写产品缩写与非完整名称，弥补纯正则难以准确匹配的不足。
6. **Pixel 3a + LSPosed**：通过设备端自动化注入，将整理后的客户信息写入安装于 Pixel 3a 的公司「科技个险」App。MacBook 在整理后连接 Pixel 3a 完成提交。

#### 用户对问题的判断

- **识别准确率并不差**：百度 OCR 在手写内容上总体可用，印刷与手写重叠仍是难点。
- **字段解释较复杂，但已有可运行的解决流程**：正则结合 DeepSeek 的语义分析，曾用于匹配字段与识别保险名称、缩写等。
- **最突出的实际痛点是系统录入和跨设备协同**：一加 15 → MacBook → server 处理 → MacBook 连接 Pixel 3a → LSPosed 向科技个险注入，造成操作链路冗长、依赖环节多。
- **不应将“旧 OCR 识别不准”误记为首要问题**，也不应仅通过更换 OCR 模型来定义新项目。
- 旧方案虽已跑通，**不代表目前仍正常运行，也不代表必须保留一加 15、Pixel 3a、LSPosed、百度 OCR、DeepSeek 或现有 server 作为未来架构**；这些仅是历史事实和可供复盘的材料。

#### 需求层面提炼（尚待确认的候选结果）

- 在保持客户信息录入结果可核验的前提下，显著减少人工中转、设备切换、手工触发与维护成本。
- 针对公司科技个险录入和个人自建库分别定义何时更新、记录何处成功以及失败后如何继续。
- 优先评估端到端工作过程，而非单点算法优化。

#### 下一步需要核实

- Pixel 3a 上 LSPosed 设备端注入本身的稳定性、成功率和必要的人为操作；以此区分“跨设备编排过于繁琐”和“公司 App 实际录入机制脆弱”两种可能不同的难点。

### BR-011：科技个险异步注入、冷却间隔与可靠性未知（用户确认，2026-10-23）

**用户确认的历史事实：**

- Pixel 3a 的 LSPosed 注入**不能连续高频地执行大量录入**；历史操作中发现注入之间需要留出**冷却时间／间隔**。
- 用户通过此前实践已经摸索并确定可使用的冷却间隔，但本轮**没有提供具体秒数**，不应杜撰。
- 因此旧方案**并非实时同步写入科技个险**，而是采用**异步处理**，由 Mac Server（用户以 MacBook 作为运行和协调节点）承担异步流程的安排与协调。
- 用户**无法确认 Pixel 3a 注入环节的真实稳定性和录入准确性**。流程曾跑通、冷却间隔已积累经验，并不等于每条记录均可靠写入、校验成功。

**业务需求推导（待确认的候选要求，而非已定技术架构）：**

- 科技个险的按需录入需允许**非实时、受速率限制的执行**，不应强制实时同步。
- 对录入任务应能区分：待处理、等待间隔、提交中、成功核验、失败待处理等不同业务状态；具体实现机制尚未定。
- 应当评估如何**核对记录是否真实成功写入科技个险**，而不是只以注入程序运行或点击提交作为成功依据。
- Mac Server 的历史协调角色应被记录，但**是否继续依赖 MacBook 或 LSPosed 尚未决定**。

**下一轮访谈重点：** 原流程如何判断某一条客户资料已成功写入科技个险；是否有核验、日志或读取回来的依据？这决定后续如何评价端到端可靠性。
