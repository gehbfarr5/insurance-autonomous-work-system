# P1-D｜自主运行、结果验证与持续改进（P1 已完成）

> **当前阅读状态：** P1 已于 2026-10-24 经用户确认完成，P2/P3 也已完成，进入 P4。本文保留 P1 访谈时点的事实、判断与缺口；当时的候选和下一步不覆盖后续决定。当前阶段见[路线图](roadmap.md)，P3 新增事实见[结项框架](p3-framework-and-p4-transition.md)。

> 更新：2026-10-24。已基于用户实际实践核对两类结果验证方式；本文件描述业务经验、方向和开放事项，不是技术实施方案或正式自动执行授权。

## 1. 已确认的长期项目方向（延续 D-001—D-019）

- AI 在约定目标、权限和边界内主动发现并执行工作，确认结果而不止提交动作；重大异常及时交接。
- AI 提出月度经营草案，与用户共同确认方向；周度自主安排授权范围内的工作，可以提出策略复评，但不单方面改变重大方向。
- 用户希望尽可能把普通重复工作交由 AI 完成，集中精力于高价值真人客户沟通与关系经营。
- 人与 AI 如何准确理解客户关系发展仍是长期共同成长的问题，当前不提前规定客户评价分级或自动判断标准。

## 2. 用户已确认的真实验证方式

### A. 科技个险中的培训体系日常任务及其他操作

- 用户描述：在**旧项目**中，科技个险培训体系日常任务的自动化实践会查看操作中的页面反馈，以判断动作后的状态。现项目已推翻旧项目重做；这只是旧项目经验，不能证明新系统已有同样能力、旧代码/流程可以复用或新系统可通过正式发布验证。
- 用户也以旧项目该应用中的其他操作说明其历史经验：不是简单做完按钮动作就假定成功，而会依据当时的界面内容继续判断。此做法尚未在重做后的新系统验证。
- 用户认为这类常规规范化操作可交由 Agent 较为自主地完成，自己不需要每天参与。
- **该系统内操作与公司活动报名并非同一工作流程或相同系统**，不能因为都涉及提交或确认结果，就将两种业务误写成同一应用中的操作。
- 旧项目没有独立统计记录证明全部操作成功率或界面变化情况下的稳健程度；新系统尚无正式发布验证。这些都应作为后续候选评估及 P3/实施阶段待验证事项。

### B. 公司活动报名（例如晚宴）

- 用户明确表示，这类活动**可以检查报名是否成功**；本人报名与代客户报名均可能存在，依活动性质决定。
- 用户有 Agent 辅助办理报名的实际经验，主观评价是**几乎没有失误**；其认识是 Agent 可以根据页面和反馈自主操作、判断与调整，而不是只能机械执行预先写死的点击脚本。
- 该评价应忠实记录为**用户既有实践经验**，不被误写为经第三方独立测量的零故障率；也不能因此断言所有类型活动都可同样自动处理。
- 页面上的成功提示、实际占用名额、确认短信或后续通知在不同活动中可能呈现不同情况；P1 只需确认**存在可验证结果的业务实践**，具体依据和例外可留在 P2/P3 的具体场景中研究。

## 3. P1-D 得到的业务认识

- **Agent 的主要区别在于能够结合当前页面状态和反馈决定后续操作**；不能仅把未来系统理解成一组固定顺序的脚本。用户看重可适应的实际完成能力和对日常人工介入的减少。
- **验证既有实践而非从零发明**：科技个险培训任务及部分活动报名已经有人工/Agent 检查结果的经验。规划应承认这一事实，不能重复将它们表述为从未实践、无法确认结果的事项。
- **仍区分真实业务结果与推断**：用户评价的稳定性值得参考，但正式覆盖范围、授权、失败恢复、效果测量等仍须在具体实施前评估。
- **不同类型任务有不同的可判定程度**：如每日任务完成、报名反馈可以通过明确结果做判断；复杂客户关系好坏尚无可靠、已定的方法。不能强行为所有工作统一一套判断标准。

## 4. 阶段结论与尚未解决的问题

**P1-D 已具备阶段性收尾条件**。明确了实际页面反馈核验经验、Agent 相对固定脚本的工作方式期待，以及哪些能力可以通过状态确认、哪些必须长远探索。
